1Bài 1 — Single-head scaled dot-product attention

Câu đồ chơi: "mèo ăn cá ngon" (4 token). Embedding giả lập bằng số ngẫu nhiên — vì mục tiêu tối nay là cơ chế attention, không phải embedding.

import torch
import torch.nn.functional as F
import math

torch.manual_seed(5)          # để kết quả của mọi người giống nhau

tokens = ["mèo", "ăn", "cá", "ngon"]
L = len(tokens)               # độ dài câu = 4
d_model = 16
d_k = 8

X  = torch.randn(L, d_model)  # "embedding" giả lập, shape (4, 16)
Wq = torch.randn(d_model, d_k)
Wk = torch.randn(d_model, d_k)
Wv = torch.randn(d_model, d_k)

Q = X @ Wq   # (4, 8)  — truy vấn: mỗi token hỏi "tôi cần gì?"
K = X @ Wk   # (4, 8)  — khóa:     mỗi token quảng cáo "tôi có gì?"
V = X @ Wv   # (4, 8)  — giá trị:   nội dung thật mang theo

Đọc kết quả

Bảng in ra là ma trận attention: hàng = token đang hỏi, cột = token được nhìn. Với causal mask, nửa trên đường chéo phải toàn số 0 — token "mèo" (đầu câu) chỉ nhìn chính nó, token "ngon" (cuối câu) được nhìn cả 4. Thử đổi seed và quan sát: pattern số 0 do mask thì luôn giữ nguyên, pattern số lớn/nhỏ do trọng số ngẫu nhiên thì đổi — đó là điểm khác giữa cấu trúc và học được.

3Bài 3 — Đo độ phức tạp: vì sao context dài "đốt điện"

Gói code Bài 1 thành hàm single_head(x) (nhận X shape (L, d_model), trả về out), rồi đo thời gian với L tăng dần:

import time

def single_head(x):
    Lx = x.shape[0]
    Qx, Kx, Vx = x @ Wq, x @ Wk, x @ Wv          # Wq/Wk/Wv của Bài 1 (d_k=8)
    s = (Qx @ Kx.T) / math.sqrt(d_k)
    s = s.masked_fill(torch.triu(torch.ones(Lx, Lx), diagonal=1).bool(),
                      float('-inf'))
    return F.softmax(s, dim=-1) @ Vx

for Lx in [64, 128, 256, 512]:
    x = torch.randn(Lx, d_model)
    t0 = time.perf_counter()
    _ = single_head(x)
    dt = time.perf_counter() - t0
    print(f"L={Lx:>4}  thời gian: {dt*1000:8.2f} ms")
✍️ TODO 7 (viết tay, không code): nhìn bảng số, trả lời 2 câu vào phần nộp bài — (1) L tăng gấp đôi thì thời gian tăng khoảng mấy lần? (2) Từ đó suy ra độ phức tạp của attention theo L là gì?
⚡ Góc tiết kiệm năng lượng: context dài gấp 8× (4k → 32k token) thì attention tốn khoảng 64× phép tính — và 64× điện năng cho cùng 1 câu trả lời. Đây chính là động lực của FlashAttention (tính theo block vừa SRAM, bớt đọc/ghi bộ nhớ), GQA (nhiều query head chia sẻ ít KV head) và KV-cache (không tính lại quá khứ khi sinh token mới). Tối nay bạn vừa đo bằng tay cái giá mà cả ngành đang tìm cách trả rẻ đi.

✓Tự kiểm tra nhanh (3 câu — bấm để hiện đáp án)

Câu 1 — Nếu bỏ phép chia cho √dk, điều gì xảy ra với softmax khi dk = 1024?
Đáp án: QKT là tổng của dk số hạng nên phương sai của nó ≈ dk — giá trị scores dao động rất lớn. Softmax của các số chênh lệch lớn sẽ bão hòa thành gần one-hot (1 token ăn gần hết trọng số), gradient qua softmax ≈ 0 → attention "chết cứng", không học được gì. Phép chia √dk giữ scores ở thang vừa phải để gradient chảy được.
Câu 2 — Vì sao causal mask bắt buộc khi train GPT, nhưng không cần khi encode cả văn bản một lần (như BERT)?
Đáp án: GPT train theo kiểu dự đoán token tiếp theo: input là token 1..t, target là token t+1. Nếu token t được nhìn thấy token t+1 trong input, mô hình "nhìn trộm đáp án" (data leakage) — loss giảm giả tạo nhưng mô hình chẳng học được gì để sinh thật. BERT không sinh tiếp mà học biểu diễn 2 chiều nên được phép nhìn cả câu.
Câu 3 — Multi-head (h=8) có tốn thêm tham số so với single-head cùng d_model không?
Đáp án: Không. WQ/WK/WV vẫn là 3 ma trận d_model×d_model (cộng thêm WO d_model×d_model) — việc chia thành 8 heads chỉ là cách tổ chức lại phép tính, không thêm trọng số. Cái được thêm là khả năng biểu diễn: 8 heads học 8 kiểu quan hệ khác nhau song song (ví dụ: head 1 bắt chủ–vị, head 2 bắt đại từ–danh từ).

⚠Bẫy thường gặp

1. Quên chia √dk. Triệu chứng: ma trận weights toàn số 0.00 và 1.00, mỗi hàng chỉ dồn vào đúng 1 cột. Attention kiểu này "điếc" — không học được quan hệ mềm nào.
2. Đặt mask sai chỗ. Mask phải gán -inf trước softmax. Nếu bạn zero-out sau softmax, các hàng không còn cộng bằng 1 nữa → phân phối xác suất bị méo, assert kiểm tra sẽ nổ ngay.
3. Reshape multi-head nhầm thứ tự chiều. .view(L, n_heads, d_k) rồi .transpose(0, 1) mới đúng. Nếu transpose trước khi view mà quên .contiguous(), PyTorch có thể báo lỗi — hoặc tệ hơn, chạy được nhưng số liệu bị xáo trộn âm thầm. Luôn kiểm tra shape sau mỗi bước reshape.
