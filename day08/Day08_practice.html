Ngày 8 — Viết prepare_data.py: ingest → normalize → dedup → split → shard

Sáng nay ta học lý thuyết: pipeline dữ liệu cần provenance và không rò rỉ eval. Tối nay ta code thật một pipeline hoàn chỉnh, sinh data_card.md và manifest hash để tái lập — đúng chuẩn một dự án train LLM nghiêm túc.

⏱️ ~60–90 phút🐍 Python 3 (chỉ dùng thư viện chuẩn)📤 Nộp code + báo cáo vào chat để được nhận xét

🎯 Mục tiêu tối nay — đầu ra phải có

  • File prepare_data.py chạy được: ingest → normalize → dedup → split → shard.
  • File data_card.md tự sinh: nguồn dữ liệu, license, thống kê, các bước lọc.
  • File manifest.json: SHA-256 từng shard + số mẫu bị loại ở từng bước.
  • Báo cáo số mẫu bị loại ở từng bước (không bao giờ chỉ báo số mẫu còn lại).

0Bối cảnh & dữ liệu

Ta sẽ tạo trước một tập dữ liệu cố ý bẩn để pipeline có cái mà lọc. Đoạn mã khởi tạo dưới đây đã viết sẵn — bạn chạy nó để sinh raw_docs.jsonl (200 tài liệu), sau đó viết pipeline xử lý.

# make_dirty_data.py — ĐÃ VIẾT SẴN, bạn chỉ cần chạy # Sinh 200 docs với các "vết bẩn" có chủ đích: # • 20 docs TRÙNG CHÍNH XÁC (copy nguyên văn) # • 15 docs GẦN TRÙNG (đổi 1-2 từ / thêm câu mở đầu) # • 10 docs chứa PII (email, số điện thoại, CMND giả) # • 10 docs rác (quá ngắn, quá dài, ký tự lặp "aaaaa...") # • 5 docs KHÁC NGÔN NGỮ (chỉ tiếng Anh thuần) # • 3 docs Ô NHIỄM EVAL (trùng nguyên văn 3 câu hỏi trong test set) # 130 docs còn lại là văn bản sạch tiếng Việt
💡 Vì sao làm vậy? Dữ liệu thật luôn bẩn. Một pipeline tốt không phải là pipeline "chạy qua" — mà là pipeline báo cáo được nó đã loại bỏ cái gì, để khi model dở ta biết đổ lỗi cho dữ liệu hay cho code.

1Bài tập chính: viết prepare_data.py

Sườn pipeline dưới đây đã có cấu trúc đầy đủ. Nhiệm vụ của bạn: tự viết phần chính trong 6 hàm có đánh dấu TODO. Mỗi hàm đều có gợi ý từng bước — mở gợi ý khi bí.

Bước 1 — normalize(text): chuẩn hóa văn bản

  1. Dùng unicodedata.normalize("NFC", ...) để gộp dấu tiếng Việt về dạng chuẩn.
  2. Xóa HTML tags, gom khoảng trắng thừa, cắt bỏ đầu/cuối.
  3. Quyết định và ghi vào data_card: có lowercase không? (gợi ý: với bài học này, KHÔNG lowercase — giữ nguyên vì viết hoa mang thông tin).
💡 Gợi ý code
# -*- coding: utf-8 -*- import re, unicodedata def normalize(text: str) -> str: # TODO 1: chuẩn hóa Unicode về NFC # TODO 2: re.sub(r"<[^>]+>", " ", text) để xóa HTML # TODO 3: re.sub(r"\s+", " ", text).strip() để gom khoảng trắng # Trả về chuỗi đã chuẩn hóa raise NotImplementedError

Bước 2 — scrub_pii(text): che thông tin nhạy cảm

  1. Dùng regex thay email thành [EMAIL], số điện thoại VN (09/03/07... 10 số) thành [PHONE].
  2. Thay dãy số ≥ 9 chữ số liên tiếp thành [ID_NUMBER] (CMND/CCCD giả).
  3. Đếm mỗi doc có bao nhiêu thực thể PII bị che — ghi vào manifest.
💡 Gợi ý regex
EMAIL_RE = re.compile(r"[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}") PHONE_RE = re.compile(r"\b0\d{9}\b") ID_RE = re.compile(r"\b\d{9,12}\b") # Dùng .subn() để vừa thay vừa đếm số lượt thay

Bước 3 — quality_filter(doc): lọc chất lượng

  1. Loại doc quá ngắn (< 30 từ) hoặc quá dài (> 2000 từ).
  2. Loại doc có tỉ lệ ký tự lặp cao: nếu ký tự thường gặp nhất chiếm > 30% độ dài → rác ("aaaaa...").
  3. Language ID đơn giản: đếm ký tự tiếng Việt có dấu (à á â ã è é ê...); nếu doc > 20 từ mà < 5% ký tự có dấu và không phải code → đánh dấu non-Vietnamese, loại.
  4. Trả về (giữ_lại: bool, lý_do_loại: str|None) — lý do loại là để báo cáo.

Bước 4 — dedup(docs): loại trùng lặp (2 tầng)

  1. Exact dedup: băm SHA-256 toàn văn bản (sau normalize) — trùng hash → loại, O(1) mỗi doc.
  2. Near dedup: với mỗi doc, tạo tập 5-gram ký tự (shingle); Jaccard similarity = |A∩B| / |A∪B|; nếu > 0.8 với doc đã giữ → loại là "gần trùng".
    Gợi ý tối ưu: so sánh tuần tự là O(n²) — với 200 docs thì OK, nhưng hãy viết comment giải thích vì sao với 1M docs ta cần MinHash/LSH (gợi ý đọc thêm).
  3. Giữ doc xuất hiện đầu tiên, loại các bản sau — thứ tự này phải deterministic (sắp xếp theo hash trước khi dedup).
💡 Gợi ý shingle + Jaccard
def shingles(text: str, k: int = 5) -> set: t = text.replace(" ", "") return {t[i:i+k] for i in range(max(1, len(t) - k + 1))} def jaccard(a: set, b: set) -> float: return len(a & b) / max(1, len(a | b)) # Loại khi jaccard > 0.8

Bước 5 — check_contamination(docs, test_set): chống rò rỉ eval ⚠️

  1. Test set cho trước: 10 câu hỏi trong test_set.jsonl (đã viết sẵn).
  2. Với mỗi doc train: nếu chứa nguyên văn một câu test (sau normalize, so sánh chuỗi con) hoặc Jaccard 8-gram > 0.9 với câu test → loại và báo cáo.
  3. Thứ tự cực kỳ quan trọng: contamination check phải chạy trước khi split train/val — vì val cũng là eval, rò rỉ vào val cũng gian lận.
⚠️ Bài học sáng nay: contamination là lỗi đạo đức khoa học, không chỉ là lỗi kỹ thuật. Một doc train chứa đáp án của câu test làm điểm eval "ảo" — model trông giỏi nhưng thực ra chỉ học thuộc.

Bước 6 — split_and_shard(docs): chia tập + chia shard + manifest

  1. Split deterministic: sắp xếp docs theo SHA-256 của nội dung, lấy 90% đầu làm train, 10% cuối làm val. (Vì sao không random.shuffle? → vì seed quên set là mất tái lập; hash-sort thì luôn giống nhau.)
  2. Shard: mỗi file .jsonl tối đa 50 docs → train-00000.jsonl, train-00001.jsonl, ... và val-00000.jsonl.
  3. Manifest manifest.json: với mỗi shard ghi sha256, num_docs, num_tokens (đếm từ đơn giản bằng split()); cộng thêm stage_report: số mẫu bị loại ở từng bước (PII count, quality, exact-dedup, near-dedup, contamination).
  4. Sinh data_card.md: nguồn dữ liệu, license (ghi rõ: dữ liệu tổng hợp cho mục đích học tập), ngày tạo, thống kê train/val, mô tả từng bước lọc + số liệu.
✅ Chạy thử: python prepare_data.py phải in ra bảng báo cáo từng bước, ví dụ:
ingest: 200 → quality: -10 → exact_dedup: -20 → near_dedup: -15 → contamination: -3 → final: 152 (train 137 / val 15)
Số liệu của bạn có thể khác chút ít tùy tham số — điều quan trọng là mọi con số đều giải thích được.

⚡ Green checkpoint — đo hiệu quả năng lượng của khâu chuẩn bị dữ liệu

Sau khi pipeline chạy xong, trả lời 2 câu hỏi trong báo cáo nộp bài:

  1. Token hữu ích / công sức: tổng số token cuối cùng chia cho số doc bị loại — mỗi doc bị loại "tốn" bao nhiêu token sạch? (Con số này cho thấy dữ liệu gốc bẩn đến mức nào.)
  2. Vì sao dedup tiết kiệm năng lượng train? Viết 2–3 câu: mỗi doc trùng lặp bị loại hôm nay giúp tiết kiệm bao nhiêu bước gradient vô ích khi train thật (gợi ý: doc trùng = model học lại điều đã biết = đốt điện vô ích).

23 câu tự kiểm tra nhanh

Không chấm điểm — tự check hiểu bài. Bấm nút để hiện đáp án.

Câu 1. Vì sao phải dedup trước khi split train/val, mà không phải sau?

✅ Vì nếu split trước, 2 bản copy của cùng một doc có thể rơi vào 2 phía: một bản ở train, một bản ở val. Khi đó val không còn "chưa từng thấy" nữa — điểm val bị thổi phồng, ta tưởng model tổng quát hóa tốt nhưng thực ra nó chỉ nhớ. Đây chính là một dạng rò rỉ eval (eval leakage).

Câu 2. Exact dedup dùng SHA-256 rất nhanh. Vậy vì sao vẫn cần thêm near-dedup bằng Jaccard/shingle?

✅ Vì dữ liệu web đầy bản "gần giống nhau": cùng một bài báo được 10 trang đăng lại, chỉ khác tiêu đề và 1–2 câu mở đầu. SHA-256 của chúng khác nhau hoàn toàn (chỉ cần 1 ký tự khác là hash khác), nên exact dedup bó tay. Near-dedup bắt được các bản này, tránh model học đi học lại cùng một nội dung — vừa tốn điện, vừa làm model thiên lệch (memorization).

Câu 3. Pipeline của bạn dùng "sắp xếp theo SHA-256 rồi cắt 90/10" thay vì random.shuffle với seed. Lợi và hại của cách này là gì?

✅ Lợi: tái lập tuyệt đối — không có seed nào để quên, chạy ở máy nào cũng ra split giống hệt nhau; không phụ thuộc implementation của RNG.
✅ Hại: thứ tự bị cố định theo hash, không "ngẫu nhiên" theo nghĩa thống kê cổ điển; nếu muốn nhiều split khác nhau (k-fold) thì phải thêm salt vào hash. Với pipeline dữ liệu học tập và sản xuất nhỏ, lợi ích tái lập thường lớn hơn.

3🪤 Bẫy thường gặp (3 lỗi dễ mắc nhất)

Bẫy 1 — Normalize "quá tay": lowercase toàn bộ + xóa dấu câu

Lowercase làm mất phân biệt "Apple (công ty)" vs "apple (trái cây)"; xóa dấu câu làm mất cấu trúc câu. Quy tắc: mỗi phép normalize phải trả lời được "thông tin nào bị mất, và ta chấp nhận mất nó vì sao" — rồi ghi câu trả lời vào data_card.md.

Bẫy 2 — Dedup sau split (đã nói ở câu tự kiểm tra 1)

Triệu chứng: val loss "đẹp bất thường", thấp hơn hẳn train loss. Cách phát hiện: kiểm tra overlap giữa train và val bằng exact hash — nếu > 0 thì pipeline sai thứ tự.

Bẫy 3 — Quên "đóng băng" thứ tự xử lý: dict/set iteration order

Trong Python, thứ tự duyệt set phụ thuộc hash randomization của phiên chạy (PYTHONHASHSEED). Nếu dedup dùng set mà không sort trước, mỗi lần chạy loại doc khác nhau → manifest hash khác nhau → mất tái lập. Cách sửa: sort theo SHA-256 của nội dung trước mọi bước có tính thứ tự.
