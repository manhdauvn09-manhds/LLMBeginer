Ngày 9 — Viết train_repro.py: seed toàn diện, checkpoint, và mô phỏng "crash"

Sáng nay ta học lý thuyết: training loop tốt phải tái lập được (chạy 2 lần ra kết quả y hệt) và hồi phục được (mất điện giữa chừng vẫn resume được). Tối nay ta code thật một training loop có cả hai tính chất, rồi chứng minh bằng thí nghiệm — không tin lời nói suông.

⏱️ ~60–90 phút🐍 Python 3 + PyTorch (CPU chạy được)📤 Nộp code + output vào chat để được nhận xét

🎯 Mục tiêu tối nay — đầu ra phải có

  • File train_repro.py chạy được: seed_everything + train loop có checkpoint đầy đủ (model, optimizer, scheduler, epoch, RNG states).
  • Thí nghiệm 1 — Tái lập: train 2 lần cùng seed → SHA-256 của trọng số cuối + loss cuối y hệt nhau.
  • Thí nghiệm 2 — Resume: train 6 epoch liên tục == train 3 epoch → lưu checkpoint → resume 3 epoch (kết quả y hệt, chứng tỏ checkpoint chứa đủ "trạng thái").
  • File run.log (loss từng epoch, JSONL) để đối chiếu 2 thí nghiệm.

0Bối cảnh — mô hình & dữ liệu

Để tập trung vào vòng lặp huấn luyện chứ không phải kiến trúc, ta dùng bài toán nhỏ nhưng đủ thật: hồi quy trên dữ liệu tổng hợp, MLP 2 lớp, Adam + StepLR. Code khởi tạo dưới đây đã viết sẵn — bạn chạy trước, sau đó mới viết vòng lặp train của mình.

# setup_day9.py — ĐÃ VIẾT SẴN, bạn chỉ cần chạy để hiểu dữ liệu import torch, torch.nn as nn torch.manual_seed(0) N, D = 2000, 20 X = torch.randn(N, D) true_w = torch.randn(D, 1) y = X @ true_w + 0.1 * torch.randn(N, 1) # hồi quy tuyến tính + nhiễu class TinyMLP(nn.Module): # mô hình nhỏ: 20 -> 64 -> 1 def __init__(self): super().__init__() self.net = nn.Sequential( nn.Linear(D, 64), nn.ReLU(), nn.Linear(64, 1)) def forward(self, x): return self.net(x) # Chia train/val: 1800 / 200 — nhớ: split này cũng phải DETERMINISTIC perm = torch.randperm(N, generator=torch.Generator().manual_seed(7))
💡 Vì sao dùng bài toán nhỏ? Vì với model lớn, một thí nghiệm crash/resume tốn hàng giờ GPU. Nguyên tắc đúng trên bài toán nhỏ sẽ giữ nguyên trên bài toán lớn — chỉ khác ở chi phí khi ta làm sai.

1Bài tập chính: viết train_repro.py

Sườn dưới đây có cấu trúc đầy đủ. Nhiệm vụ của bạn: tự viết phần chính trong các hàm đánh dấu TODO. Mỗi bước đều có gợi ý — mở khi bí.

Bước 1 — seed_everything(seed): gieo hạt toàn diện

  1. Set seed cho random, numpy, torch (CPU) và torch.cuda (nếu có GPU).
  2. Bật chế độ deterministic: torch.backends.cudnn.deterministic = True và torch.backends.cudnn.benchmark = False — và hiểu vì sao 2 dòng này phải đi đôi với nhau (xem Bẫy 2).
  3. Trả về seed để ghi vào log — vì một thí nghiệm không ghi lại seed của nó thì không thể gọi là "tái lập".
💡 Gợi ý code
import random, numpy as np, torch def seed_everything(seed: int) -> int: random.seed(seed) np.random.seed(seed) torch.manual_seed(seed) # TODO: thêm torch.cuda.manual_seed_all(seed) nếu torch.cuda.is_available() # TODO: 2 dòng cudnn deterministic/benchmark # (nâng cao) torch.use_deterministic_algorithms(True) — có thể làm 1 số op báo lỗi, # với MLP này thì an toàn return seed

Bước 2 — train_one_run(seed, epochs, ckpt_path=None, resume_from=None): vòng lặp train

  1. Gọi seed_everything(seed) đầu tiên — trước cả khi tạo model và DataLoader (vì nn.Linear khởi tạo trọng số bằng RNG của torch).
  2. DataLoader: shuffle=True nhưng truyền generator=torch.Generator().manual_seed(seed) — đây là điểm 90% tutorial trên mạng bỏ sót: shuffle của DataLoader dùng RNG riêng, không ăn theo torch.manual_seed.
  3. Mỗi epoch: train 1 vòng → tính train loss + val loss → scheduler.step() → ghi 1 dòng JSON vào run.log: {"epoch": e, "train_loss": ..., "val_loss": ..., "lr": ...}.
  4. Cuối mỗi epoch: gọi save_checkpoint(...) (Bước 3).
  5. Nếu resume_from khác None: load checkpoint trước vòng lặp, tiếp tục từ epoch+1.
💡 Gợi ý DataLoader deterministic
g = torch.Generator().manual_seed(seed) loader = torch.utils.data.DataLoader( train_ds, batch_size=64, shuffle=True, generator=g) # Lưu ý: nếu dùng num_workers > 0, cần thêm worker_init_fn gieo seed # cho từng worker — nếu không, thứ tự batch giữa 2 lần chạy sẽ khác nhau.

Bước 3 — save_checkpoint / load_checkpoint: checkpoint ĐẦY ĐỦ

  1. Checkpoint phải chứa 6 thứ: epoch, model_state_dict, optimizer_state_dict, scheduler_state_dict, rng_states (python/numpy/torch/cuda), seed.
  2. rng_states: random.getstate(), np.random.get_state(), torch.get_rng_state() (+ cuda nếu có). Khi resume, phục hồi cả 4 — nếu không, thứ tự batch và dropout/noise sau điểm resume sẽ khác, kết quả "gần giống" nhưng không y hệt.
  3. Quy ước tên file: ckpt_epoch{E}.pt. Chỉ giữ checkpoint mới nhất + mỗi 3 epoch một bản (đỡ tốn đĩa).
💡 Gợi ý cấu trúc checkpoint
ckpt = { "epoch": epoch, "seed": seed, "model": model.state_dict(), "optimizer": opt.state_dict(), # chứa momentum buffers của Adam! "scheduler": sched.state_dict(), # chứa step count của StepLR "rng": { "python": random.getstate(), "numpy": np.random.get_state(), "torch": torch.get_rng_state(), # "cuda": torch.cuda.get_rng_state_all() nếu có GPU }, } torch.save(ckpt, path)

Bước 4 — Thí nghiệm 1: chứng minh TÁI LẬP

  1. Chạy train_one_run(seed=42, epochs=6) hai lần độc lập (2 process riêng càng tốt).
  2. Sau mỗi lần chạy, tính SHA-256 của model.state_dict() (nối bytes của mọi tensor) và loss cuối.
  3. Tiêu chí pass: 2 hash y hệt nhau, 2 loss y hệt nhau đến chữ số thập phân cuối cùng. Nếu chỉ "gần bằng" → còn chỗ rò rỉ randomness, quay lại Bước 1–2 tìm.

Bước 5 — Thí nghiệm 2: mô phỏng CRASH và resume

  1. Run A (liên tục): train_one_run(seed=42, epochs=6) — lưu hash cuối H_A.
  2. Run B (gián đoạn): train 3 epoch → "sập nguồn" (dừng chương trình, xóa model khỏi RAM cho chắc) → tạo model mới → load_checkpoint("ckpt_epoch3.pt") → resume 3 epoch còn lại — lưu hash cuối H_B.
  3. Tiêu chí pass: H_A == H_B và loss từng epoch 4,5,6 của 2 run y hệt nhau. Đây là bằng chứng checkpoint của bạn chứa đủ trạng thái — thiếu optimizer state hay RNG state là fail ngay.
⚠️ Bài học sáng nay: "resume được" không có nghĩa là "train tiếp được". Resume đúng nghĩa là không ai phân biệt được run bị gián đoạn với run chạy liền mạch — kể cả máy tính. Tiêu chí H_A == H_B chính là định nghĩa đó.

⚡ Green checkpoint — resume tốt tiết kiệm bao nhiêu điện?

Sau khi 2 thí nghiệm pass, trả lời 2 câu hỏi trong báo cáo nộp bài:

  1. Tính toán cụ thể: giả sử train một LLM nhỏ tốn 10 ngày trên 8 GPU, điện + thuê máy ~2.000 USD/ngày. Nếu crash ở ngày thứ 7 mà không có checkpoint, thiệt hại là bao nhiêu? Nếu có checkpoint mỗi 6 giờ, thiệt hại còn bao nhiêu? (Viết phép tính, không cần chính xác tuyệt đối.)
  2. Đánh đổi: checkpoint mỗi 6 giờ "tốn" thời gian ghi đĩa. Vì sao với LLM lớn, chi phí ghi checkpoint (vài phút) luôn rẻ hơn chi phí mất trắng (vài ngày)? Nêu 1 trường hợp mà checkpoint quá thường xuyên lại gây hại.

23 câu tự kiểm tra nhanh

Không chấm điểm — tự check hiểu bài. Bấm nút để hiện đáp án.

Câu 1. Checkpoint đã có model.state_dict() và optimizer.state_dict(). Vì sao vẫn cần lưu thêm rng_states? Không lưu thì chuyện gì xảy ra khi resume?

✅ Vì sau điểm resume, thứ tự các batch (do DataLoader shuffle) và mọi randomness còn lại (dropout, noise) đều do RNG quyết định. Không phục hồi RNG state, run resume sẽ thấy các batch theo thứ tự khác → gradient khác → trọng số sau vài epoch chệch dần khỏi run liên tục. Triệu chứng điển hình: loss "gần giống" nhưng hash trọng số khác — fail tiêu chí H_A == H_B.

Câu 2. Bạn đã gọi seed_everything(42) đầy đủ, nhưng 2 lần chạy vẫn ra kết quả khác nhau. Liệt kê 3 "thủ phạm" cần kiểm tra đầu tiên.

✅ 1. DataLoader shuffle: chưa truyền generator có seed riêng (thủ phạm số 1). 2. cudnn benchmark: benchmark=True cho phép cuDNN tự chọn thuật toán nhanh nhất mỗi lần chạy — thuật toán khác nhau cho kết quả float khác nhau ở chữ số cuối. 3. Thứ tự tạo object: gọi seed_everything sau khi đã tạo model/DataLoader — lúc đó RNG đã bị "tiêu thụ" một đoạn, seed không còn tác dụng như mong đợi. (Ngoài ra: num_workers>0 thiếu worker_init_fn, hoặc dùng op không-deterministic mà chưa bật use_deterministic_algorithms.)

Câu 3. Vì sao checkpoint lưu optimizer.state_dict() (chứa momentum của Adam) mà không chỉ lưu trọng số model? Điều gì xảy ra nếu resume mà khởi tạo optimizer mới từ đầu?

✅ Adam không chỉ dùng gradient hiện tại — nó dùng trung bình động của gradient (momentum) và bình phương gradient tích lũy từ nhiều bước trước. Khởi tạo optimizer mới = xóa sạch "trí nhớ" này → vài chục/vài trăm bước đầu sau resume, hướng đi của optimizer khác hẳn → loss chệch khỏi run liên tục. Với LLM train hàng tuần, sai lệch này có thể làm mất cả ngày công "warm-up" lại optimizer.

3🪤 Bẫy thường gặp (3 lỗi dễ mắc nhất)

Bẫy 1 — Chỉ lưu model.state_dict(), quên optimizer + scheduler

Triệu chứng: resume xong loss "nhảy" bất thường ở epoch đầu tiên sau resume, rồi mới ổn định lại. Cách phát hiện: so sánh loss epoch 4 của run A và run B trong Thí nghiệm 2 — khác nhau là dính bẫy. Quy tắc: checkpoint = toàn bộ trạng thái có nhớ (stateful), không chỉ trọng số.

Bẫy 2 — Bật cudnn.benchmark = True cùng lúc với deterministic

benchmark=True bảo cuDNN: "mỗi lần chạy hãy đo và chọn thuật toán nhanh nhất" — mà thuật toán được chọn có thể khác nhau giữa 2 lần chạy, cho kết quả float khác nhau ở chữ số cuối. Nó vô hiệu hóa ngầm mọi cố gắng deterministic. Quy tắc: khi cần tái lập, luôn deterministic=True, benchmark=False — chấp nhận chậm hơn một chút để đổi lấy tính tái lập.

Bẫy 3 — Checkpoint ở mức epoch nhưng resume kỳ vọng ở mức step

Nếu crash giữa epoch 4 (đã train được 70% số batch), checkpoint epoch 3 bắt ta train lại cả epoch 4 từ đầu — các batch đã thấy sẽ bị thấy lần 2, thứ tự dữ liệu chệch khỏi run liên tục → fail H_A == H_B. Cách sửa thật: với bài tập này, checkpoint theo epoch là đủ (ta "crash" đúng biên epoch); nhưng hãy viết 1 đoạn comment trong code giải thích: với LLM thật, checkpoint phải ở mức step (lưu cả vị trí trong DataLoader) thì resume mới chính xác.
