Ngày 10 — Viết health_checks.py: "bác sĩ trực" cho training loop

Sáng nay ta học chẩn đoán: NaN, loss spike, gradient explosion, batch trùng lặp, token ngoài phạm vi. Tối nay ta biến checklist chẩn đoán thành code chạy tự động: cắm monitor vào training loop, rồi cố ý "phá" run bằng 3 thí nghiệm để chứng minh monitor bắt đúng lỗi — không tin lời nói suông.

⏱️ ~60–90 phút🐍 Python 3 + PyTorch (CPU chạy được)📤 Nộp code + output vào chat để được nhận xét

🎯 Mục tiêu tối nay — đầu ra phải có

  • File health_checks.py chạy được: kiểm tra NaN/Inf (loss, trọng số, gradient), grad norm, token ngoài range, batch trùng, loss spike.
  • HealthMonitor cắm vào training loop theo đúng thứ tự checklist: dữ liệu trước → loss/gradient sau.
  • 3 thí nghiệm phá run (đã viết sẵn demo_train.py): monitor phải "hú còi" đúng lỗi đã cài — ghi lại cảnh báo đầu tiên của mỗi thí nghiệm.
  • Hàm smoke_test(50 bước): loss giảm, không NaN, grad norm ổn định → mới dám chạy full run (Green checkpoint của khóa học).

0Bối cảnh — vòng lặp train nhỏ để cắm monitor

Bài toán: language model tí hon (embedding → MLP → dự đoán token tiếp theo) trên dữ liệu tổng hợp. File demo_train.py bên dưới đã viết sẵn — bạn chạy trước để hiểu luồng, sau đó mới viết health_checks.py của mình ở mục 1.

# demo_train.py — ĐÃ VIẾT SẴN, bạn chỉ cần đọc + chạy import torch, torch.nn as nn from health_checks import HealthMonitor, HealthAlert, grad_norm # <- bạn viết file này VOCAB, D, H, SEQLEN = 64, 16, 32, 8 loss_fn = nn.CrossEntropyLoss() def make_model(seed=42): torch.manual_seed(seed) model = nn.Sequential( # LM tí hon: embed -> MLP -> logits nn.Embedding(VOCAB, D), nn.Flatten(1), nn.Linear(D * SEQLEN, H), nn.ReLU(), nn.Linear(H, VOCAB)) opt = torch.optim.AdamW(model.parameters(), lr=3e-4) return model, opt def train_step(model, opt, batch, targets): opt.zero_grad() loss = loss_fn(model(batch), targets) loss.backward() gn = grad_norm(model) # bắt mạch trước khi update opt.step() return loss.item(), gn def run_experiment(name, fault_fn, steps=30): model, opt = make_model() # mỗi thí nghiệm bắt đầu từ model khỏe mạnh mon = HealthMonitor(vocab_size=VOCAB) print(f"\n===== {name} =====") first_alert = None for step in range(steps): batch, targets = fault_fn(step, opt) # 3 hàm fault cài "bệnh" khác nhau try: alerts = mon.check_batch(batch, step) # (1) dữ liệu TRƯỚC forward loss, gn = train_step(model, opt, batch, targets) alerts += mon.check_step(loss, model, step) # (2) loss/grad SAU backward except HealthAlert as e: # lỗi nghiêm trọng -> dừng run ngay print(f" [step {step}] 🛑 DỪNG RUN: {e}") first_alert = first_alert or f"HealthAlert: {e}" break for a in alerts: print(f" [step {step}] ⚠️ {a}") first_alert = first_alert or a if step % 10 == 0: print(f" [step {step}] loss={loss:.4f} grad_norm={gn:.3f}") print(f" 👉 Cảnh báo đầu tiên: {first_alert}") # 3 thí nghiệm: mỗi hàm trả về (batch, targets) có cài "bệnh" (xem mục 2) if __name__ == "__main__": run_experiment("TN1: batch trùng lặp", fault_duplicate) run_experiment("TN2: learning rate bùng nổ", fault_lr_spike) run_experiment("TN3: token ngoài phạm vi", fault_bad_token)
💡 Thứ tự kiểm tra chính là checklist sáng nay: check_batch (dữ liệu) chạy trước forward — vì 90% vấn đề nằm ở dữ liệu; check_step (loss, gradient) chạy sau backward. Kiểm tra NaN sau opt.step() sẽ không biết NaN đến từ forward hay backward — nên ta kiểm tra ngay sau khi có loss.

1Bài tập chính: viết health_checks.py

Sườn dưới đây có cấu trúc đầy đủ. Nhiệm vụ của bạn: tự viết phần chính trong các chỗ đánh dấu TODO. Mỗi TODO đều có gợi ý — mở khi bí, nhưng hãy tự nghĩ trước 5 phút.

Lắp ráp — HealthMonitor (đã viết sẵn, bạn đọc hiểu)

class HealthMonitor: """Cắm vào training loop. Thứ tự = checklist chẩn đoán: dữ liệu -> loss/grad.""" def __init__(self, vocab_size, ratio=5.0, max_consecutive=3): self.spike = SpikeDetector(ratio, max_consecutive) self.dedup = BatchDedup() self.vocab_size = vocab_size def check_batch(self, batch, step): # Gọi TRƯỚC forward: token range là LỖI CHÍ MẠNG (forward chắc chắn crash) # -> fail fast bằng HealthAlert. Batch trùng chỉ cảnh báo (train vẫn chạy được). fatal = check_token_range(batch, self.vocab_size, step) if fatal: raise HealthAlert("; ".join(fatal) + " — dừng trước khi forward crash") return self.dedup.step(batch, step) def check_step(self, loss, model, step): # Gọi SAU backward, TRƯỚC opt.step(): NaN/Inf + loss spike. # SpikeDetector có thể raise HealthAlert -> demo_train.py sẽ dừng run. return check_finite(loss, model, step) + self.spike.step(loss, step)
⚠️ Vì sao không gộp tất cả vào một hàm? Vì check_batch phải chạy trước model(batch) — một batch chứa token ngoài range sẽ làm nn.Embedding crash trước khi monitor của bạn kịp lên tiếng. Thứ tự kiểm tra là một phần của thiết kế, không phải chi tiết trang trí.

2Thí nghiệm: cố ý "phá" run, xem monitor có bắt được không

Ba hàm fault_* dưới đây đã viết sẵn — bạn thêm vào demo_train.py rồi chạy python demo_train.py. Mỗi thí nghiệm cài đúng một "bệnh" từ bài sáng nay. Nhiệm vụ: ghi lại cảnh báo đầu tiên của mỗi thí nghiệm và đối chiếu với kỳ vọng.

# Thêm vào demo_train.py — 3 "bệnh" đã cài sẵn def _rand_batch(): return (torch.randint(0, VOCAB, (32, SEQLEN)), torch.randint(0, VOCAB, (32,))) _DUP = None def fault_duplicate(step, opt): """Dataloader 'kẹt': steps 5-9 trả ĐÚNG một batch lặp lại.""" global _DUP if _DUP is None: _DUP = _rand_batch() return _DUP if 5 <= step < 10 else _rand_batch() def fault_lr_spike(step, opt): """Bug lịch trình LR: step 5 learning rate nhảy 3e-4 -> 2.0.""" for g in opt.param_groups: g['lr'] = 2.0 if step == 5 else 3e-4 return _rand_batch() def fault_bad_token(step, opt): """Một batch chứa token id = VOCAB (ngoài phạm vi từ điển).""" b, t = _rand_batch() if step == 5: b[0, 0] = VOCAB return b, t

🔬 Vì sao TN3 chứng minh "thứ tự kiểm tra là thiết kế"?

Thử comment dòng mon.check_batch(...) trong run_experiment rồi chạy lại TN3: nn.Embedding sẽ ném IndexError (hoặc CUDA assert) và không một cảnh báo thân thiện nào được in ra. Monitor tốt không chỉ kiểm tra đúng thứ — mà còn kiểm tra đúng lúc.

💡 Mẹo chẩn đoán mang về: khi run thật của bạn có biểu hiện lạ, hãy chạy lại với HealthMonitor cắm sẵn và đọc cảnh báo đầu tiên — nó thường chỉ đúng nguyên nhân gốc, trước khi các triệu chứng thứ cấp (spike → NaN) che lấp mọi thứ.

3Tự kiểm tra nhanh (không chấm điểm)

3 câu hỏi — bấm "Hiện đáp án" để tự đối chiếu.

Câu 1. Bạn thấy grad norm nhảy từ 0.8 lên 12.4 trong 3 bước, loss spike 2 lần liên tiếp. Theo checklist "dữ liệu → shape → loss → optimizer → precision", việc đầu tiên nên làm là gì?

✅ Kiểm tra dữ liệu/batch trước: log loss từng batch để tìm batch "độc" nào gây spike, xem lại learning rate/schedule có vừa thay đổi không. Bật clip_grad_norm_ nếu chưa có. Không vội tăng kích thước mô hình hay đổi kiến trúc — 90% vấn đề nằm ở 2 bước đầu của checklist, và "chữa" một run đang spike bằng cách tăng model chỉ làm mọi thứ tệ hơn.

Câu 2. Phân biệt weight_decay và gradient clipping — mỗi cái một câu, nói rõ chúng kiểm soát cái gì.

✅ Weight decay kiểm soát độ lớn của trọng số (kéo trọng số về gần 0 mỗi bước — chống phình trọng số và overfit). Gradient clipping kiểm soát độ lớn của bước cập nhật (cắt gradient khi chuẩn vượt ngưỡng — chống explosion). Hai cơ chế bổ sung, không thay thế nhau. Nhớ thêm: đừng áp weight decay lên bias và LayerNorm.

Câu 3. 5 epoch gần nhất: train loss 0.31 → 0.29 (tiếp tục giảm), val loss 0.45 → 0.62 (tăng trở lại). Đây là overfit hay underfit? Xử lý thế nào?

✅ Overfit — train/val gap mở rộng, val loss quay đầu tăng là dấu hiệu kinh điển. Xử lý: tăng weight decay, thêm dropout, tăng dữ liệu huấn luyện, hoặc dừng sớm (early stopping) tại điểm val loss thấp nhất. Đây là lúc HealthMonitor của bạn có thể mở rộng thêm: theo dõi train/val gap mỗi epoch và cảnh báo khi gap mở rộng 3 epoch liên tiếp.

4🪤 Bẫy thường gặp

Bẫy 1 — Chỉ log loss, bỏ qua grad norm

Loss trông "bình thường" không có nghĩa là run khỏe. Grad norm vọt là tiền thân của NaN — đến khi loss thành NaN thì đã muộn, vì bạn mất luôn manh mối nguyên nhân gốc. Quy tắc: log grad norm mỗi bước, không chỉ mỗi epoch.

Bẫy 2 — Ngưỡng cảnh báo đặt theo cảm tính

Spike 1 lần đã kill run → giết nhầm run đang khỏe (spike đơn lẻ thường tự hồi phục). Chờ 10 spike mới báo → tốn GPU vô ích. Ngưỡng phải đến từ thí nghiệm: chạy thử, xem spike "lành" và spike "ác" khác nhau thế nào, rồi mới chốt số (ví dụ ratio > 5, 3 lần liên tiếp).

Bẫy 3 — Kiểm tra NaN sai thời điểm

Kiểm tra NaN sau opt.step() thì khi phát hiện NaN, bạn không biết nó đến từ forward (dữ liệu/model) hay từ bước cập nhật (optimizer/LR). Kiểm tra ngay sau khi có loss (trước opt.step()) — mỗi kiểm tra phải trả lời được câu hỏi "lỗi xuất hiện ở khâu nào".
