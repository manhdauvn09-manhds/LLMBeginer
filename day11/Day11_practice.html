Scaling Lab: từ 9 run nhỏ đến quyết định ngân sách

Bài thực hành gắn với bài sáng "Scaling law: dùng để lập ngân sách, không phải khẩu hiệu". File này thuộc khóa Trở thành AI Engineer (LLM) — ôn lại công thức C ≈ 6·N·D, xem lại bài sáng tại đây nếu cần.

⏱️ Dự kiến: 60–90 phút 🐍 Python + PyTorch + numpy 📦 Đầu ra: scaling_lab.py + bảng 9 run + prediction vs actual

🎯 Mục tiêu buổi tối

  • Hiểu scaling law bằng tay làm thật: train 3 kích thước mô hình × 3 token budget = 9 run, ghi loss theo compute.
  • Fit đường log-log đơn giản, rồi dự báo loss cho run thứ 10 trước khi train thật → so sánh prediction vs actual.
  • Luyện quyết định ngân sách đúng kiểu engineer: chọn run dựa trên cải thiện loss / kWh, không phải "model càng to càng tốt".
  • Green checkpoint ⚡: chọn run tối đa hóa cải thiện loss/kWh, không tối đa hóa tham số.

Phần B — train thật (9 run, chạy qua đêm)

Dùng tiny char-level GPT (mẫu karpathy) trên file text ~200 KB. Bước 0 — smoke test bắt buộc: chạy đúng 1 run S1 với 50 bước trước — nếu loss không giảm mượt thì dừng, sửa bug rồi mới chạy full (đây là thói quen "mọi experiment có smoke test" của bài sáng Ngày 10–11).

# Quy ước grid — copy vào file train của bạn: CONFIGS = { "S": dict(n_layer=2, n_embd=64, n_head=2), # ~0.4M params "M": dict(n_layer=4, n_embd=128, n_head=4), # ~1.2M params "L": dict(n_layer=6, n_embd=192, n_head=6), # ~3.0M params } TOKEN_BUDGETS = [50_000, 150_000, 400_000] # D cho mỗi run # steps = D // (batch_size * block_size); mỗi bước dùng đúng budget, không "train cho đã" # Ghi vào runs.jsonl mỗi run: name, N (đếm thật bằng sum(p.numel())), D, loss cuối, walltime
Budget là hợp đồng: khi hết token budget thì dừng — kể cả loss vẫn đang giảm. Đó chính là ý nghĩa "scaling law dùng để lập ngân sách": quyết định trước, không chạy theo cảm xúc.
Đầu ra buổi tối: (1) file scaling_lab.py với 3 TODO đã điền, (2) bảng 9 run (của bạn hoặc của mẫu + ghi rõ nguồn), (3) prediction vs actual cho run 10 — nếu chưa train kịp run 10 thì ghi "chưa chạy", không đoán mò.

2Tự kiểm tra nhanh (không chấm điểm)

Bấm "Hiện đáp án" để tự đối chiếu — trung thực với chính mình là đủ.

Câu 1. Vì sao run S2 (0.4 M params, 150 k tokens, C = 3.6e11) đạt loss 2.87 tốt hơn run M1 (1.2 M params, 50 k tokens, C = 3.6e11) dù compute bằng nhau?
Vì compute-optimal: với cùng ngân sách C, chia cho data (token) thường "lời" hơn đổ vào tham số khi model đang thiếu data — đúng kết luận Chinchilla trong bài sáng. Nếu cứ tăng N mà D không tăng, model đói data, loss không cải thiện tương xứng.
Câu 2. Khi fit đường log-log, ta fit log10(loss) theo log10(C) thay vì fit thẳng loss theo C. Vì sao?
Vì dạng power law loss = a·C^b trở thành tuyến tính trên thang log: log(loss) = log(a) + b·log(C). Fit tuyến tính đơn giản, ổn định số học (C trải nhiều bậc 10^11–10^12), và hệ số b chính là "độ dốc cải thiện" — mỗi lần tăng C gấp 10 thì loss nhân với 10^b.
Câu 3. "Chọn run tối đa hóa cải thiện loss/kWh" — vì sao tiêu chí này quan trọng với người quan tâm tiết kiệm năng lượng?
Vì loss tuyệt đối thấp nhất thường đến từ run to nhất — nhưng mỗi điểm loss cuối cùng có thể "tốn" gấp chục lần điện so với run nhỏ hơn. Tiêu chí loss/kWh tìm điểm ngọt mà mỗi kWh bỏ ra vẫn mang lại cải thiện đáng kể — đúng Green checkpoint của buổi học, và là cách ra quyết định ngân sách của một AI engineer thực thụ.

3Bẫy thường gặp

3 lỗi dễ mắc nhất khi làm lab kiểu scaling:

  • So sánh 9 run với learning rate khác nhau. Loss chênh nhau có thể do LR chứ không phải do scale. Khóa LR (hoặc scale LR theo rule cố định, ví dụ µP đơn giản) cho cả 9 run — chỉ khác N và D.
  • Đo "budget" bằng epoch thay vì token. 1 epoch trên corpus khác nhau = token khác nhau. Scaling law nói về D = số token thực sự nhìn thấy, không phải số vòng lặp. Luôn log D thật.
  • Nhầm "loss plateau" với "đã tới giới hạn scaling". Plateau ở run nhỏ thường là do hết data đa dạng / LR sai, không phải scaling law hết hiệu lực. Trước khi kết luận, kiểm tra checklist Ngày 10 (data → shape → loss → optimizer → precision).
