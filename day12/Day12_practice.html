Phần A — EM & F1 (mở rộng từ bài sáng)

import json, math, random

def normalize(s: str) -> str:
    """Viết thường, gom khoảng trắng."""
    return " ".join(s.lower().strip().split())

def exact_match(pred: str, gold: str) -> int:
    return int(normalize(pred) == normalize(gold))

def f1(pred: str, gold: str) -> float:
    p, g = normalize(pred).split(), normalize(gold).split()
    common = sum(min(p.count(w), g.count(w)) for w in set(g))
    if common == 0:
        return 0.0
    prec, rec = common / len(p), common / len(g)
    return 2 * prec * rec / (prec + rec)

#         rồi dự đoán bằng tay EM và F1 trước khi chạy code kiểm chứng.
qa_tests = [
    ("Thủ đô Hà Nội", "hà nội"),
    ("hà nội", "hà nội"),
    ("Paris", "paris"),
    # ("", "<đáp án chuẩn>"),
]

for pred, gold in qa_tests:
    print(f"pred={pred!r:28} gold={gold!r:12} EM={exact_match(pred,gold)} F1={f1(pred,gold):.2f}")

Phần C — Bootstrap CI: đừng tin chênh lệch 1–2%

Bạn có kết quả đúng/sai của 500 câu hỏi cho 2 phiên bản model. Hãy bootstrap 1000 lần để ra khoảng tin cậy 95%, rồi quyết định "mới có thật sự tốt hơn không".

random.seed(42)  # reproducibility: cùng seed → cùng kết quả

# Kết quả mẫu: 1 = đúng, 0 = sai. Model mới đạt 82%, cũ 80%.
old = [1]*400 + [0]*100
new = [1]*410 + [0]*90
random.shuffle(old); random.shuffle(new)

def bootstrap_ci(scores, n_boot=1000, alpha=0.05):
    means = []
    n = len(scores)
    for _ in range(n_boot):
        sample = [random.choice(scores) for _ in range(n)]
        means.append(sum(sample) / n)
    means.sort()
    lo = means[int((alpha/2) * n_boot)]
    hi = means[int((1 - alpha/2) * n_boot)]
    return sum(scores)/n, lo, hi

acc_old, lo_old, hi_old = bootstrap_ci(old)
acc_new, lo_new, hi_new = bootstrap_ci(new)
print(f"Cũ: {acc_old:.0%}  CI=[{lo_old:.0%}, {hi_old:.0%}]")
print(f"Mới: {acc_new:.0%} CI=[{lo_new:.0%}, {hi_new:.0%}]")

2 · Tự kiểm tra nhanh (không chấm điểm)

Câu 1 — Vì sao phải dùng seed cố định trong bootstrap CI?

Vì bootstrap dùng random sampling có hoàn lại. Không seed → mỗi lần chạy ra CI khác nhau → kết quả không tái lập được (reproducible). Eval chuẩn phải: cùng code + cùng dữ liệu + cùng seed → cùng con số. Đây cũng là lý do file regression_set và task set phải được version (lưu commit hash).

Câu 2 — Model mới 82% vs model cũ 80%, CI đều ±4%. Tuyên bố "mới tốt hơn" được không?

Không. Hai khoảng [78%, 86%] và [76%, 84%] chồng lấn → chênh 2% có thể chỉ là may rủi của bộ đề. Đúng chuẩn phải nói "chưa đủ bằng chứng", rồi hoặc thu thêm dữ liệu eval, hoặc chấp nhận hòa. Nguyên tắc vàng buổi sáng: không số liệu trên cùng một bộ eval = cảm giác.

Câu 3 — Bạn phát hiện 1 câu hỏi trong eval set trùng nguyên văn với dữ liệu train. Việc này làm điểm số thay đổi theo hướng nào, và bước khắc phục đầu tiên là gì?

Điểm bị thổi phồng (model chỉ nhớ đáp án, không chứng tỏ năng lực). Bước đầu tiên: loại bỏ câu đó (và mọi n-gram trùng lặp ≥ 8 từ) khỏi train HOẶC loại câu đó khỏi eval set, rồi chạy lại eval. Lâu dài: nhúng canary string vào eval set và giữ bộ đề quan trọng nhất bí mật, không public.

3 · Bẫy thường gặp

  • Bootstrap mà quên shuffle/cố định seed: kết quả CI thay đổi mỗi lần chạy, rồi tự nhủ "lần này mới tốt hơn thật". Luôn random.seed(...) và ghi lại seed trong report.
  • F1 cao nhưng EM = 0 rồi kết luận model "sai hoàn toàn": hai metric đo hai thứ khác nhau — F1 đo độ gần đúng, EM đo khớp tuyệt đối. Với đáp án dài/tự do, F1 (hoặc LLM-judge có rubric) mới là metric chính; EM chỉ hợp với đáp án ngắn, chuẩn.
  • Regression set viết toàn prompt khó: sai mục đích — regression set là "phanh xe", chỉ để phát hiện hồi quy (đúng → sai). Prompt khó/chưa làm được thuộc về task set. Trộn lẫn hai loại thì mỗi lần chạy đều đỏ, mất tác dụng cảnh báo.
