🛠️ Ngày 27 — Buổi tối: Thực hành serving LLM

Serving hiệu quả là bài toán hệ thống — tự tay đo KV cache, prefill/decode, mô phỏng PagedAttention + continuous batching, rồi kiểm chứng speculative decoding bằng số liệu thật.

⏱️ Ước lượng: Phần A ~25 phút · Phần B ~20 phút · Phần C ~15 phút · Tự kiểm tra ~5 phút

🎯 Mục tiêu buổi tối

  1. Đo được KV cache / token và TTFT / TPOT trên một mô hình Transformer nhỏ chạy thật — thấy tận mắt decode là memory-bound.
  2. Mô phỏng PagedAttention (cấp phát theo block) và continuous batching — đo được mức lãng phí bộ nhớ và thời gian chờ giảm bao nhiêu so với cách naive.
  3. Tính được tốc độ tăng của speculative decoding theo tỉ lệ chấp nhận α — và biết khi nào nó không còn thắng.

Kiến thức nền (1 dòng): buổi sáng đã học — prefill xử lý cả prompt cùng lúc nên compute-bound, decode sinh từng token nên memory-bound; KV cache là nút thắt bộ nhớ số 1 của serving; PagedAttention, continuous batching và speculative decoding là 3 đòn bẩy chính.

Phần A — Đo KV cache + prefill vs decode (25 phút)

Bài tập chính

Nhiệm vụ: Dùng một Transformer nhỏ (4 lớp, d_model=256 — dùng lại mô hình mini-GPT của bạn từ các ngày trước, hoặc dùng khung dưới đây), đo 3 thứ: (1) kích thước KV cache thực tế mỗi token, (2) thời gian prefill theo độ dài prompt, (3) thời gian decode mỗi token.

Bước 1 — Tính KV cache bằng công thức trước

Trước khi chạy code, tính tay trên giấy với mô hình của bạn:

# Công thức buổi sáng:
# KV cache / token = 2 (K và V) × n_layer × d_model × bytes_per_param
# FP16 = 2 byte; FP32 = 4 byte
# Ví dụ: 4 lớp, d_model=256, FP16 → 2 × 4 × 256 × 2 = 4096 byte/token ≈ 4 KB/token
# Một request 2.000 token → ~8 MB; 64 request đồng thời → ~512 MB
# TODO: thay số của mô hình BẠN dùng và ghi kết quả ra giấy trước khi chạy.

Bước 2 — Khung code: đo prefill và decode

import time, torch
import torch.nn as nn

# Mô hình nhỏ: dùng lại mini-GPT của bạn, hoặc khung tối giản này
# (chỉ cần 1 block Transformer có hỗ trợ use_cache kiểu KV cache)
class Block(nn.Module):
    def __init__(self, d=256, n_head=4):
        super().__init__()
        self.attn = nn.MultiheadAttention(d, n_head, batch_first=True)
        self.ln1, self.ln2 = nn.LayerNorm(d), nn.LayerNorm(d)
        self.mlp = nn.Sequential(nn.Linear(d, 4*d), nn.GELU(), nn.Linear(4*d, d))
    def forward(self, x, kv=None):
        # kv: (K, V) đã cache từ các token trước; None = prefill
        q = self.ln1(x)
        if kv is None:
            out, _ = self.attn(q, q, q, need_weights=False)
            new_kv = None  # TODO: tách K, V ra để cache (gợi ý: dùng attn.in_proj_weight)
        else:
            K, V = kv
            # TODO: nối K, V mới vào cache, rồi attention với K, V đầy đủ
            out, _ = self.attn(q, K, V, need_weights=False)
            new_kv = (K, V)
        x = x + out
        x = x + self.mlp(self.ln2(x))
        return x, new_kv

# Gợi ý đơn giản hơn (được chấp nhận ở bài này):
# - Prefill: cho cả prompt (n token) qua mô hình 1 lần, bấm giờ.
# - Decode: cho từng token một qua mô hình, bấm giờ mỗi bước,
#   cộng dồn cache bằng cách giữ lại hidden state / KV của các bước trước.
# - Đo KV cache: dùng torch.cuda.memory_allocated() trước/sau khi cache
#   đầy (nếu chạy CPU: đếm số phần tử cache × 4 byte cho FP32).

Phần B — Mô phỏng PagedAttention + continuous batching (20 phút)

Nhiệm vụ: Không cần GPU — mô phỏng bằng Python thuần, với 20 request giả lập có độ dài ngẫu nhiên (50–500 token). So sánh naive vs PagedAttention (bộ nhớ), static batching vs continuous batching (thời gian chờ).

Phần C — Nâng cao (15 phút, làm nếu còn sức)

  1. Speculative decoding bằng số: giả sử draft model đoán đúng trung bình α token mỗi lần kiểm chứng (α = 0, 1, 2, 3, 4), mỗi lần kiểm chứng tốn 1 lần đọc trọng số model lớn + chi phí draft không đáng kể. Tốc độ tăng ≈ α + 1 token / lần đọc (token cuối do model lớn sửa). Vẽ bảng α → speedup, rồi trả lời: với văn bản khó đoán (α ≈ 0.5) còn đáng dùng không? Draft model phải nhanh hơn model lớn bao nhiêu lần thì mới có lãi?
  2. Prefix caching: 20 request có chung system prompt 200 token. Tính KV cache tiết kiệm được nếu chia sẻ block prefix (gợi ý: dùng công thức Phần A) và thời gian prefill tiết kiệm được (dùng số đo TTFT ở Phần A). Khi nào prefix caching KHÔNG giúp gì?
  3. Quantized serving: tính lại KV cache / token ở Phần A nếu chuyển FP16 → INT8 (1 byte). Decode nhanh lên khoảng bao nhiêu lần theo lý thuyết (vì decode memory-bound)? Rồi đối chiếu với Day 25: cái giá phải trả là gì, đo bằng cách nào?

✅ Tự kiểm tra nhanh (3 câu — bấm để hiện đáp án)

Câu 1. Vì sao decode lại memory-bound trong khi prefill lại compute-bound, dù cả hai đều chạy cùng một mô hình?
Prefill xử lý nhiều token cùng lúc nên mỗi lần đọc trọng số được "chia" cho nhiều token — GPU có đủ phép tính để làm, giới hạn nằm ở tốc độ tính toán. Decode mỗi bước chỉ xử lý 1 token nhưng vẫn phải đọc toàn bộ trọng số + toàn bộ KV cache — lượng tính toán ít, lượng dữ liệu phải đọc nhiều, nên GPU phần lớn thời gian chờ đọc bộ nhớ. Cùng một mô hình, khác tỉ lệ "tính toán / dữ liệu đọc" nên khác nút thắt.
Câu 2. PagedAttention không hề thay đổi mô hình, vì sao nó vẫn làm throughput tăng vài lần?
Vì nó gỡ nút thắt bộ nhớ: cấp phát naive giữ chỗ tối đa cho mọi request ngay từ đầu nên phần lớn VRAM bị "đặt trước" mà không dùng tới — batch size bị giới hạn bởi bộ nhớ lãng phí, GPU chạy rỗi. PagedAttention cấp phát theo block đúng nhu cầu thực tế, gần như không lãng phí, nên cùng một GPU chứa được nhiều request đồng thời hơn → GPU luôn có việc làm → throughput tăng mà mô hình không đổi gì.
Câu 3. Speculative decoding cho ra kết quả giống hệt chạy model lớn thuần túy, nhưng quantization thì không. Vì sao khác nhau? Trường hợp nào bạn chọn quantization thay vì speculative decoding?
Speculative decoding chỉ dùng draft model để đề xuất token, mọi token cuối cùng đều được model lớn kiểm chứng (token sai bị sửa), nên đầu ra giống hệt model lớn. Quantization thay đổi chính trọng số và phép tính của model lớn nên đầu ra có thể khác (mất chính xác). Chọn quantization khi: bộ nhớ/VRAM là nút thắt (model không vừa GPU, KV cache quá lớn), hoặc cần giảm chi phí mỗi request; chọn speculative decoding khi: chất lượng đầu ra không được phép thay đổi và văn bản đủ dễ đoán (code, template) để draft đoán đúng thường xuyên.

⚠️ Bẫy thường gặp

  1. Đo TTFT/TPOT mà không warm-up: lần chạy đầu tiên bao gồm cả thời gian load mô hình, compile kernel, cấp phát bộ nhớ — con số sẽ cao gấp nhiều lần thực tế. Luôn chạy warm-up 2–3 lần rồi mới bấm giờ, và báo rõ "đã warm-up".
  2. Báo "100 tokens/giây" mà không nói bối cảnh: đó là throughput hệ thống hay tốc độ 1 request? Batch size bao nhiêu? Prompt dài bao nhiêu? Thiếu 3 thông tin này thì con số gần như vô nghĩa — đúng tinh thần Day 24: đo tốc độ thực trong điều kiện thực.
  3. Quên KV cache khi tính bộ nhớ serving: chỉ tính trọng số mô hình rồi kết luận "vừa GPU" là sai — với nhiều request đồng thời, KV cache có thể lớn gấp nhiều lần trọng số (xem ví dụ buổi sáng: 16 request × 4.000 token ≈ 32 GB). Luôn cộng cả hai trước khi chọn GPU / batch size.

⚡ Góc tiết kiệm năng lượng

Serving là nơi LLM "đốt" năng lượng nhiều nhất trong vòng đời — huấn luyện một lần, phục vụ hàng triệu request. Ba cách tiết kiệm lớn nhất đều là bài toán hệ thống: chọn model nhỏ nhất đạt SLO thay vì model lớn nhất có thể; cap context và độ dài output (mỗi token thêm vào đều tốn KV cache + thời gian decode); autoscale theo tải thay vì luôn bật tối đa. Bài tập tối nay đo đúng điểm này: TTFT/TPOT và KV cache chính là "hóa đơn năng lượng" của mỗi request.
