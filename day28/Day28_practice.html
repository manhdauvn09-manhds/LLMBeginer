MỤC TIÊU BUỔI TỐI

Cuối buổi bạn có: (1) một bảng số đo thật của 6 cấu hình trên cùng prompt set, (2) một biểu đồ Pareto frontier do chính bạn vẽ, (3) một cấu hình bị loại vì bị chi phối + một cấu hình được chọn kèm lý do theo SLO. Không có cấu hình "tốt nhất tuyệt đối" — chỉ có lựa chọn đúng cho sản phẩm của bạn.

Kiến thức nền cần nhớ (1 dòng): cấu hình bị chi phối = tồn tại cấu hình khác tốt hơn hoặc bằng nó ở mọi trục; điểm trên frontier thì muốn cải thiện một trục phải hy sinh một trục khác.

Phần A — Benchmark công bằng 6 cấu hình (~30 phút)

Thiết lập thí nghiệm. Trước khi viết code, viết rõ câu này vào đầu file (quy tắc Day 24 + Day 28):

📝 "Thứ duy nhất thay đổi là ___" — mỗi lần chạy chỉ đổi một biến: dtype, hoặc batch size, hoặc use_cache. Mọi thứ khác — cùng prompt set, cùng concurrency, cùng warmup, cùng phần cứng — giữ nguyên. So sánh INT8 batch 32 với FP16 batch 1 rồi kết luận "INT8 nhanh gấp 5 lần" là kết luận vô giá trị.

* Trên CPU, FP16 thường không nhanh hơn FP32 — đó chính là một phát hiện đáng ghi lại, không phải lỗi. Nếu máy bạn có GPU, chạy lại cùng 6 cấu hình trên GPU và so sánh frontier hai lần chạy.

Ba trục đo, trên cùng một prompt set cố định:

  • Chất lượng: perplexity (PPL) trên 10 câu cố định — càng thấp càng tốt. Quantization làm mất bao nhiêu điểm phải đo, không đoán.
  • Độ trễ: TTFT (thời gian tới token đầu) và TPOT (thời gian mỗi token tiếp theo), báo p50 và p95, không chỉ trung bình. Chạy mỗi cấu hình 3 lần, báo trung bình ± độ lệch.
  • Năng lượng: Joules/request ≈ công suất trung bình × thời gian / số request. Trên CPU dùng công suất giả định (ghi rõ, vd 65 W cho laptop, 250 W cho GPU) hoặc codecarbon nếu cài được. Quan trọng là cùng một cách tính cho mọi cấu hình.

"""Benchmark 6 cấu hình serving — Ngày 28, Mini-project 4.
Chạy:  python benchmark.py
Kết quả: in bảng quality / latency / energy + lưu results.json
"""
import json, time
import numpy as np
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer

MODEL = "distilgpt2"
# Cùng prompt set cho MỌI cấu hình — không đổi giữa các lần chạy.
PROMPTS = [
    "The future of artificial intelligence is",
    "To save energy, a data center should",
    "The capital of France is",
    "In machine learning, overfitting means",
    "A transformer model uses attention to",
    "The quick brown fox jumps over",
    "Renewable energy is important because",
    "To train a neural network, we need",
    "The largest planet in the solar system is",
    "A good benchmark should measure",
]
# Câu cố định để tính perplexity (chất lượng) — không trùng prompt set.
PPL_TEXTS = [
    "The cat sat on the mat and looked out of the window.",
    "Machine learning models learn patterns from data.",
    "The sun rises in the east and sets in the west.",
]
ASSUMED_WATTS = 65.0   # GHI RÕ giả định: 65 W CPU laptop; đổi thành 250 nếu chạy GPU
N_REPS = 3             # mỗi cấu hình chạy 3 lần, báo trung bình ± độ lệch
WARMUP = 3             # bỏ qua vài request đầu để máy ổn định

CONFIGS = [
    {"name": "A", "dtype": torch.float32, "batch": 1,  "use_cache": True},
    {"name": "B", "dtype": torch.float32, "batch": 8,  "use_cache": True},
    {"name": "C", "dtype": torch.float16, "batch": 1,  "use_cache": True},
    {"name": "D", "dtype": torch.float16, "batch": 8,  "use_cache": True},
    {"name": "E", "dtype": torch.float16, "batch": 32, "use_cache": True},
    {"name": "F", "dtype": torch.float32, "batch": 8,  "use_cache": False},
]

def load(dtype):
    tok = AutoTokenizer.from_pretrained(MODEL)
    tok.pad_token = tok.eos_token
    m = AutoModelForCausalLM.from_pretrained(MODEL, torch_dtype=dtype)
    m.eval()
    return tok, m

@torch.no_grad()
def perplexity(tok, model, texts):
    """PPL trung bình trên các câu cố định — càng thấp càng tốt."""
    total_nll, total_tok = 0.0, 0
    for t in texts:
        ids = tok(t, return_tensors="pt").input_ids
        out = model(ids, labels=ids)
        n = ids.shape[1] - 1
        total_nll += out.loss.item() * n
        total_tok += n
    return float(np.exp(total_nll / total_tok))

@torch.no_grad()
def time_one_config(tok, model, cfg):
    """Đo TTFT + TPOT trên prompt set, trả về (ttft_p50, ttft_p95, tpot_p50, tpot_p95, joules/request)."""
    ttfts, tpots = [], []
    t0 = time.perf_counter()
    for r in range(WARMUP + N_REPS * 2):
        # Gom prompt thành batch theo cfg["batch"]
        for i in range(0, len(PROMPTS), cfg["batch"]):
            batch = PROMPTS[i:i + cfg["batch"]]
            enc = tok(batch, return_tensors="pt", padding=True)
            start = time.perf_counter()
            out = model.generate(**enc, max_new_tokens=16,
                                 do_sample=False, use_cache=cfg["use_cache"],
                                 pad_token_id=tok.eos_token_id)
            # Ước lượng thô: TTFT ~ thời gian prefill (lần generate đầu),
            # TPOT ~ (tổng thời gian - TTFT) / (số token - 1).
            # Muốn tách chính xác TTFT/TPOT từng token: dùng streamer
            # hoặc generate từng bước (xem gợi ý ở Phần A, bước 3).
            elapsed = time.perf_counter() - start
            ttfts.append(elapsed / len(batch))          # xấp xỉ: thời gian/request
            tpots.append(elapsed / len(batch) / 16)     # xấp xỉ: thời gian/token
    total = time.perf_counter() - t0
    n_req = (WARMUP + N_REPS * 2) * len(PROMPTS)
    joules = ASSUMED_WATTS * total / n_req
    return (float(np.percentile(ttfts, 50)), float(np.percentile(ttfts, 95)),
            float(np.percentile(tpots, 50)), float(np.percentile(tpots, 95)), joules)

def main():
    results = []
    for cfg in CONFIGS:
        print(f"\n=== Cấu hình {cfg['name']}: dtype={cfg['dtype']}, "
              f"batch={cfg['batch']}, use_cache={cfg['use_cache']} ===")
        print("Thứ duy nhất thay đổi là:", cfg)  # kiểm chứng: chỉ 1 biến đổi
        tok, model = load(cfg["dtype"])
        ppl = perplexity(tok, model, PPL_TEXTS)
        ttft50, ttft95, tpot50, tpot95, joules = time_one_config(tok, model, cfg)
        print(f"PPL={ppl:.2f} | TTFT p50={ttft50*1000:.0f}ms p95={ttft95*1000:.0f}ms | "
              f"TPOT p50={tpot50*1000:.1f}ms | Năng lượng={joules:.1f} J/req")
        results.append({"name": cfg["name"], "ppl": ppl,
                        "ttft_p50": ttft50, "ttft_p95": ttft95,
                        "tpot_p50": tpot50, "joules_per_req": joules})
        del model
        torch.cuda.empty_cache() if torch.cuda.is_available() else None
    json.dump(results, open("results.json", "w"), indent=2)
    print("\nĐã lưu results.json — sang Phần B để tìm frontier.")

if __name__ == "__main__":
    main()

Bước 2 — Chạy và ghi bảng số đo thật của bạn (đừng dùng số ví dụ dưới đây — đó chỉ là minh họa cách trình bày):

A (FP32, b1)…………
B (FP32, b8)…………
C (FP16, b1)…………
D (FP16, b8)…………
E (FP16, b32)…………

Ghi kèm bối cảnh vào bảng: phần cứng (CPU/GPU cụ thể), ASSUMED_WATTS, số lần lặp, nhiệt độ nếu biết. Không có bối cảnh thì số không tái tạo được.

Bước 3 (nâng cao, tùy chọn) — Tách TTFT/TPOT thật từng token: thay model.generate bằng vòng lặp model(input_ids, use_cache=True) từng bước: đo thời gian của bước prefill đầu tiên (= TTFT), rồi thời gian trung bình mỗi bước decode tiếp theo (= TPOT). So sánh với ước lượng thô ở khung trên — chênh lệch bao nhiêu? Vì sao?

💡 Gợi ý kiểm chứng nhanh: cấu hình F (tắt KV cache) phải chậm hơn rõ rệt so với B ở cùng batch 8 — nếu không, kiểm tra xem use_cache=False có thực sự được truyền vào generate không. Cấu hình E (batch 32) trên CPU có thể chậm hơn D vì bộ nhớ — đó là dữ liệu thật, ghi lại, đừng "sửa" cho đẹp.

Phần C — Chọn theo SLO + Green checkpoint (~15 phút)

Bây giờ đóng vai người ra quyết định. Viết 3 lựa chọn, mỗi lựa chọn 2–3 câu, dựa trên frontier của chính bạn:

  1. Chatbot tương tác (SLO: TTFT p95 < 300 ms, người dùng chờ từng token): chọn điểm nào trên frontier? Vì sao không chọn điểm rẻ nhất, cũng không chọn điểm chính xác nhất?
  2. Tác vụ batch offline (SLO: rẻ nhất có thể, PPL tăng tối đa 5% so với FP32 là chấp nhận được): chọn điểm nào? Tiết kiệm được bao nhiêu % năng lượng so với cấu hình FP32 batch 1?
  3. Green checkpoint: chỉ ra một cấu hình bạn đã loại vì bị chi phối, và một cấu hình bạn chọn kèm lý do theo SLO. Nếu mọi cấu hình đều "ngon" thì bạn chưa đo đủ trục — thường là thiếu trục năng lượng hoặc thiếu p95. Quay lại Phần A và đo thêm.

✅ Tự kiểm tra nhanh (3 câu)

Câu 1 — Cấu hình X có PPL 24, TTFT p95 400 ms, 30 J/req. Cấu hình Y có PPL 22, TTFT p95 350 ms, 25 J/req. X có bị Y chi phối không?
Có. Y tốt hơn X ở cả ba trục (PPL 22 < 24, TTFT 350 < 400, năng lượng 25 < 30) nên X bị chi phối — loại X ngay, không cần tranh cãi, dù X "trông vẫn ổn".
Câu 2 — Vì sao phải báo TTFT p95 mà không chỉ báo trung bình? Cho một tình huống cụ thể mà trung bình đẹp nhưng p95 xấu.
Trung bình giấu trải nghiệm tệ nhất. Ví dụ: 19/20 request trả lời trong 100 ms nhưng 1 request kẹt hàng đợi 3 giây vì tới đúng lúc batch đang đầy — trung bình vẫn đẹp (~245 ms) nhưng 5% người dùng "đen đủi" phải chờ 3 giây. p95 bắt được đúng nhóm này, và p95 xấu là dấu hiệu hàng đợi tắc lúc tải cao.
Câu 3 — Bạn so sánh INT8 batch 32 với FP16 batch 1, thấy INT8 nhanh gấp 5 lần và kết luận "INT8 nhanh hơn FP16". Kết luận này sai ở đâu, và cách so sánh đúng là gì?
Sai vì đã đổi hai biến cùng lúc (quantization + batch size) — đó là so sánh batch size, không phải so sánh quantization. Cách đúng: giữ batch size bằng nhau (vd cùng batch 8), chỉ đổi dtype, rồi mới kết luận về quantization; muốn kết luận về batch thì giữ dtype bằng nhau, chỉ đổi batch.

🪤 Bẫy thường gặp

  • Chỉ báo một con số duy nhất ("120 tokens/giây") rồi kết luận cấu hình tốt — không có trục chất lượng đi kèm thì không biết đã mất bao nhiêu chính xác để đổi lấy tốc độ; không có p95 thì không biết người dùng chậm nhất chờ bao lâu.
  • Đo lúc máy vừa khởi động, không warmup: vài chục request đầu đo cả "khởi động" (load model, cấp phát bộ nhớ, GPU chưa ổn định), không phải "phục vụ". Luôn warmup rồi mới đo.
  • So sánh ở concurrency khác nhau: một cấu hình thắng ở concurrency 1 có thể thua ở concurrency 16. So sánh phải cùng concurrency, và năng lượng phải đo ở concurrency thực tế, không phải chạy lẻ một request lúc máy rỗi.
